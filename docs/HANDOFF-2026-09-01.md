## What shipped

A **Marketing section** — a new top-level nav group with two screens:

- `/marketing-overview` — spend, leads, cost per lead, patients, cost per patient
- `/marketing-campaigns` — one row per campaign, ordered by spend, with tier badges

Gated on module key `marketing` (agency-toggleable per sub-account) plus permission
`marketing.view`. **Reception can never see it** (project rule 5) — enforced at both the
permission defaults and the route guard, with a behavioural regression test.

Behind it:

1. **Attribution ingest.** `lib/integrations/ghl-attribution.js` — `extractAttribution()`
   and `parseGadCampaignId()`, both pure. Wired into `contactRow()`.
2. **Opportunistic fill.** The nightly walk already holds every contact; attribution is
   now written for any contact whose columns are still empty, gated on
   `attribution_captured_at IS NULL`. No backfill worker, no extra API calls.
3. **Conversion RPC.** `ad_lead_conversions(p_org, p_since, p_until, p_practice)` — did a
   GHL lead become a Dentally patient, by email or last-10-digit phone.
4. **Aggregation.** `marketing.repository.js` / `marketing.service.js` join spend to leads,
   producing cost per lead and cost per patient in integer pence.
5. **Endpoint.** `GET /api/marketing/performance?scope=&since=&until=`.

## The three findings this design rests on

All from read-only probes against live Plan4growth connections. **Do not re-litigate these
without re-running the probes.**

### 1. Google lead forms are an empty well

Customer `6846708190` spends ~£3,100/month across 6 enabled campaigns (40k impressions,
2,045 clicks, ~125 conversions in 30 days) and has **one lead form asset with zero
submissions in 30 days**. Its conversions are calls and local actions, not form fills:
`Calls From Ads` 52, `Clicks to call` 23, directions 108, website visits 102, other
engagements 448. Every `WEBPAGE` form-fill conversion action is REMOVED and at 0.

`lead_form_submission_data` would return nothing. Out of scope.

### 2. Meta lead retrieval is unobtainable

261 `OUTCOME_LEADS` campaigns, 28 of 35 active ad sets on `destination_type = ON_AD` —
genuine Instant Forms whose leads *are* retrievable in principle. But `leads_retrieval`
requires App Review **and Business Verification**, and the owner cannot verify the app.
**Abandoned, not deferred.**

> `docs/META_APP_REVIEW.md` predates this decision and now contradicts it. Treat this
> handoff as authoritative; that doc should be retired or annotated.

### 3. GoHighLevel already carries campaign- and ad-level attribution

The finding that replaced the dead plan. `GET /contacts/?locationId=` returns a non-empty
`attributions[]` on **100/100** contacts, in the **list** response — so it costs **zero
extra API calls** on top of the pull that already runs nightly.

```json
{ "utmSessionSource": "Paid Social", "adSource": "facebook", "medium": "facebook",
  "utmSource": "facebook", "utmCampaign": "Dental Implant Open Day Sept 26",
  "utmCampaignId": "120249721894530517", "utmAdId": "120249722055010517",
  "utmMedium": "Photos | 35+ | 258K | 03/08/26", "utmContent": "AD 2", "isFirst": true }
```

**Field names matter.** The list endpoint uses `utm`-prefixed keys (`utmCampaignId`,
`utmAdId`, `utmGclid`); the single-contact GET uses bare `campaignId`/`adId` for the same
values. We read the list shape — a reader written against the other shape silently finds
nothing on every contact.

**The join is verified against live spend:** `utmCampaignId 120249721894530517` →
`ad_metrics` meta_ads campaign "Dental Implant Open Day Sept 26", £1,472.65 spend, 105,437
impressions, 2,400 clicks, 10–31 Aug 2026.

Measured coverage (2,400 contacts, 4 subaccounts): `attributions[]` present on **92.3%**;
`utmCampaignId` *and* `utmAdId` on **55.6%**.

**Google attributes through a different key.** Paid Search carries no `utmCampaignId` — it
carries `utmGclid` on **305/305**, plus the campaign id embedded in the landing page URL
(`?gad_source=1&gad_campaignid=22794584316&gclid=…`). This also confirms Google leads are
landing-page fills flowing into GHL, not native lead forms.

## Traps hit — each one cost real time

**`SECURITY DEFINER` + `SET search_path` block SQL-function inlining.** The RPC was planned
*generically* with `p_org` unknown and never chose the index probes: **11,136 ms**, against
**608 ms** for the byte-identical query inline. Fix is `plpgsql` + `RETURN QUERY EXECUTE …
USING`, which forces a custom plan per call → **55 ms**. This is also why the SQL editor
lies: literals get a custom plan, parameters get a generic one. **30 other `p_org` RPCs
have this shape.**

**A heterogeneous array upsert NULLs columns across the whole batch.** `postgrest-js` sends
`?columns=<union of every row's keys>` with `defaultToNull`, so omitting a key *per row*
does not protect it — one attributed contact in a 500-row chunk wipes attribution on every
unattributed contact beside it. Fixed by grouping rows by full column-set signature.

**Never `.slice(0,10)` a London ISO instant to get a date.** `londonISO()` emits
`2026-07-31T23:00:00Z` for 1 Aug in BST, so slicing shifts the window a day and drops the
31st. Use `londonYmd()` from `lib/tz.js`.

**Expression indexes are fragile.** `right(regexp_replace(...))` indexes were never chosen
by the planner; rewriting as per-lead `EXISTS` probes made it **worse (50 s)**. STORED
generated columns (`contacts.email_norm`, `contacts.phone10`) plus plain btree are what the
planner costs correctly.

**`requireRole` makes a permission key decorative.** Gating a `.view` endpoint on role means
the Team Permissions matrix renders a toggle that changes nothing. Use `requirePermission`.

## Design correction not reflected in the spec

The spec's §1 table says attribution writes to **`leads`**. It was implemented on
**`contacts`** — attribution arrives in the contact pull and is contact-level (one person,
one first touch), while a contact may own several leads, so per-lead storage would duplicate
it and let the copies disagree. Reads join `leads → contacts`. The plan records the
correction; the spec text was not back-fixed.
