# Plan: Dentally sync + CSV manual feed (real data)

Generated by /plan-eng-review on 2026-05-25

## Problem

Overview/finance/clinical screens run on mock data. Wire them to real data via two
ingestion paths: (1) a Dentally API-token integration that polls every 30 minutes,
(2) a CSV manual feed for orgs without Dentally. Both land in the same tables so the
existing analytics endpoints light the screens up.

## Scope (agreed)

IN: 3 core datasets — patients→`contacts`, appointments→`appointments`,
payments→`payments`. Real Dentally REST sync (incremental, 30-min poll) + CSV import
for the same 3 datasets. Token entry reuses the existing broker key-paste flow.

OUT (deferred): treatments/UDA sync, the extra CSV templates (financials, treatment_plans,
leads), CSV dual-approval staging, wiring the remaining mock sections (growth/ops/wealth/training),
reconciliation engine. See "NOT in scope".

## Locked decisions (from review)

1. **Idempotency**: add `source` + `external_id` to `payments`; partial UNIQUE
   `(organisation_id, source, external_id) WHERE external_id IS NOT NULL` on
   `contacts`/`appointments`/`payments`. Upsert onConflict that composite. Source
   namespaces Dentally vs manual vs stripe — no cross-source collisions.
2. **Practice mapping**: add `practices.pms_site_id`. Resolve Dentally site_id / CSV
   `practice_code` against it. Unmatched = explicit failure (CSV per-row error;
   sync logs `last_error` + skips). No silent default.
3. **CSV flow**: direct validated upsert + row-level error report. `source='manual'`.
   No staging/approval (deferred TODO).
4. **CSV parser**: add `csv-parse` dependency.

## Data flow

```
DENTALLY (every 30 min, node-cron */30)
  workers/index.js → dentally-sync.syncAllOrgs()
    └─ for each active integration (per-org try/catch)
         syncOneOrg(org, integ)
           since = integ.last_sync_at ?? now-30d
           contactsMap = bulk SELECT contacts(pms_external_id→id) for org   ← avoids N+1
           pullPatients     → fetchAllPages(/patients?since)     → upsert contacts
           pullAppointments → fetchAllPages(/appointments?since) → resolve practice+contact → upsert appointments
           pullPayments     → fetchAllPages(/payments?since)     → resolve practice+contact → upsert payments (amount*100)
           on 429 → honour Retry-After; on error → last_error + status='failed'
           on success → last_sync_at = now

CSV (POST /api/files/import, multipart)
  parse (csv-parse) → per-row validate (types, required, practice_code resolves,
  amount→pence) → upsert valid rows (source='manual', composite key) → return
  { imported: n, rejected: [{row, reason}] }

Both write via serviceClient with explicit .eq('organisation_id', orgId).
```


## Dentally client facts (from elevate-complete/04-integrations/DENTALLY_SETUP.md)

- Regional base URL (UK `api.dentally.co`, sandbox `api.sandbox.dentally.co`) → store in `integration.config.base_url`.
- `Authorization: Bearer <apiKey>` (already decrypted by `authHeader()`); **mandatory `User-Agent` header** or requests rejected.
- Rate limit ~10 req/s; back off on 429 `Retry-After`.
- Pagination: `page` + `per_page=100`, `meta.total_pages`, responses wrapped in a key. **Date filter mandatory** (use `since`).
- Use native `fetch` + a small token-bucket (no axios; backend is ESM, native fetch).

## Failure modes

| Path | Failure | Test? | Handled? | User sees |
|------|---------|-------|----------|-----------|
| Dentally pull | token expired/invalid | yes | last_error + status=failed | Integration page error chip |
| Dentally pull | 429 rate limit | yes | Retry-After backoff | transparent |
| Dentally pull | one org throws | yes | per-org try/catch | other orgs sync |
| sync/CSV | unmatched practice | yes | skip+error / row reject | CSV report; sync log |
| CSV | malformed amount/date | yes | row reject + reason | error report |
| CSV | duplicate re-upload | yes (CRITICAL) | composite-key upsert | no dupes |

## UI Design (from /plan-design-review)

Classification: APP UI (utilitarian admin/data screens). Design system = app
`components/ui` + `globals.css` tokens; reference prototype `launch-manual-feed`
(line 28684) and `launch-health` (28523). No DESIGN.md, no new components.

**Placement (decided):** CSV upload + staging-approval + integration-health all live
under the existing **System** section (folded in, not a new Launch Control section).
They appear in the System SectionTabs bar.

**CSV partial-success (decided):** result screen shows a green "N imported" summary +
an inline `DataTable` of rejected rows (row #, bad value, plain-English reason). User
fixes the source file and re-uploads; re-import is idempotent (composite key), so no
dupes. No all-or-nothing; one bad row never blocks good rows.

**Interaction states (added to plan):**
```
SURFACE             | LOADING         | EMPTY                       | ERROR                    | SUCCESS              | PARTIAL
--------------------|-----------------|-----------------------------|--------------------------|----------------------|-------------------------
CSV upload          | btn spinner     | "Pick a dataset, drop file" | banner: parse/size/type  | toast "N imported"   | -> result report
                    | "Validating…"   |                             |                          |                      |
CSV result report   | -               | "All rows clean"            | per-file failure card    | green summary card    | DataTable of rejects
Staging queue       | skeleton rows   | EmptyState "No batches      | load-error banner        | "Approved" StatusBadge| "N pending your approval"
(approval)          |                 | awaiting approval"          |                          |                      | + uploader!=approver: approve disabled w/ tooltip
Integration connect | "Connecting…"   | provider cards (exist)      | "Test failed: <reason>"  | green Chip "Synced 2m"| "token expiring" warn Chip
/test/last-sync     | btn disabled    |                             | last_error shown on card |                      |
Xero OAuth          | redirect spinner| -                           | "Authorisation failed"   | connected + tenant    | -
```
Reuse `EmptyState`, `Chip`, `StatusBadge`, `DataTable`, toast. Uploader≠approver: the
approve button is disabled for the uploader with a tooltip ("A different user must
approve") — server still enforces 403; UI just prevents the dead click.

**Responsive/a11y (baked):** screens are tables/forms — single-column stack under 768px,
file input + select keyboard-reachable, 44px touch targets, status not conveyed by colour
alone (Chip carries text label too).
